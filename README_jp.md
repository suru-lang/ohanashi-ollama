# ohanashi-ollama(おはなし)

手元のコンピューターで動く [Ollama](https://ollama.com/) の LLM と、ブラウザでおしゃべりする Web アプリです。サーバーは日本語のプログラミング言語「[する](https://github.com/suru-lang/suru)」で書いてあり、1つの実行ファイルになります。

- モデルを画面で選べます(Ollama に入っているモデルの一覧から)。新しい会話には、モードに合うおすすめのモデルを選びます
- 会話ごとに「💬 会話」と「🛠 コーディング」のモードを切り替えられます。コーディングにすると、コーディング向けの決まりとリポジトリの決まり(`OHANASHI.md` など)を読み、「💻 砂場」を使います
- 「🧠 モデル帳」: 起動するとモデルの大きさ・能力を記録し、ウェブ検索が使えれば、モデルに特徴と点数(コード・会話・日本語・推論)を調べさせて SQLite にしまいます。調べたモデルが小さければ、大きなモデルで調べ直します。⚙ で見て、手で直せます
- 会話は SQLite のファイルにしまうので、閉じても続きから話せます。左の一覧から前の会話を開けます
- 会話の中に話題ごとの「スレッド」を作れます(見出しの「＋ スレッド」)。モデルに送るのはそのスレッドの発言だけなので、長くなっても速いままです。リポジトリ・指示・モデルなどの設定は会話のものを、どのスレッドでもそのまま使います。前のスレッドで決めたことは、会話の「📒 メモ」に書いて(答えの「メモに足す」でも)次のスレッドに持ち越せます
- 左の「会話を探す」で、題と発言の中身からスレッドを探せます。開くと見つかった所に印が付きます
- 答えは届いたところから少しずつ出ます。「止める」で途中で止められます(そこまでの答えは残ります)
- 答えの Markdown(コード・箇条書き・表など)を整えて出し、コードは「写す」でコピーできます
- 会話ごとに、指示(システムプロンプト)と温度を決められます
- 「コードを書くときの決まり」のような、モデルに守ってほしい「📜 決まり」を名前を付けてしまっておき、⚙ で会話に付けられます(いくつでも)。決まりは答えるたびに読むので、直すと付けているすべての会話に効きます。新しい会話に最初から付ける決まりも選べます。砂場か GitHub を使う答えでは、作業フォルダのリポジトリの `OHANASHI.md`(なければ `AGENTS.md`・`CLAUDE.md`)も決まりとして読みます
- 考えるモデル(qwen3・deepseek-r1 など)の考えている途中の文や、砂場・GitHub の道具を使った跡は、「途中経過」にたたんで出します(押すと開きます)
- 「💻 砂場」を押しておくと、モデルが Docker のコンテナの中でコードを書いて動かし、結果を確かめてから答えます(Docker と、道具を使えるモデルが要ります)。会話ごとに、コンテナからインターネットにつないで pip・apt を使えるようにもできます
- 最後の答えを「作り直す」、失敗したら「もう一度」
- 答えの速さ(トークン/秒)を出します
- 「🌐 ウェブ」を押しておくと、ウェブで調べてから答えます。答えの終わりに出典が付きます(自分で動かす SearXNG か、Ollama の API キーが要ります)
- 「🐙 GitHub」を押しておくと、モデルが会話に足した GitHub のリポジトリ(設定・ファイルの一覧・ファイル・issue と PR)を読んでから答えます。リポジトリは会話ごとに ⚙ の設定で足し、「読むだけ」か「読み書き」を選びます。読み書きのリポジトリには、頼めば issue を作る・直す・コメントする・閉じることや、「💻 砂場」で clone して直したものを push して PR を作ることもできます
- 画像・PDF・文字のファイルを、画面に落とす・入力欄に貼る・📎 で選ぶ、で問いに添えられます。画像は見えるモデル(qwen2.5vl・gemma3 など)が読み、PDF と文字のファイルは文を取り出して、どのモデルにも読ませます
- ほかのタブやアプリを見ている間に答えが終わると、タブの題の頭に「✅」(失敗は「⚠️」)が付きます。⚙ の「🔔 見ていない間に答えが終わったら通知する」に印を付けると、ブラウザの通知も出ます(押すとその会話に戻ります)
- スマートフォンの幅でも使えます。暗い色の設定にも合わせます

## 動かし方

要るもの:

- [Ollama](https://ollama.com/download) と、モデルを1つ以上(`ollama pull llama3.2` など)
- する 本体 0.9.1 以上(`kumu` と clang)。入れ方は [する の README](https://github.com/suru-lang/suru#入れ方)
- libsqlite3 と OpenSSL(`kumu` が足りなければ入れ方を出します)
  - macOS: `brew install sqlite openssl@3` と `export PKG_CONFIG_PATH="$(brew --prefix sqlite)/lib/pkgconfig:$(brew --prefix openssl@3)/lib/pkgconfig"`
  - Debian・Ubuntu: `sudo apt install libsqlite3-dev libssl-dev`

```sh
git clone https://github.com/suru-lang/ohanashi-ollama
cd ohanashi-ollama
kumu 実行
```

起動したら、ブラウザで http://localhost:8080/ を開きます。画面のファイルは今のフォルダの `画面/` から読むので、このフォルダで起動してください。

### 引数

```sh
kumu 実行 -- --port 9000 --db ~/おはなし.db
./出力/ohanashi-ollama --ollama http://192.168.1.10:11434
```

| 引数 | 意味 | 既定 |
|---|---|---|
| `--ollama URL` | Ollama の場所 | 環境変数 `OLLAMA_HOST`、なければ `http://localhost:11434` |
| `--listen アドレス` | 画面を開くアドレス(`0.0.0.0` ならほかの機械からも開ける) | `127.0.0.1`(同じ機械の中からだけ) |
| `--port ポート` | 画面を開くポート | 8080 |
| `--db ファイル` | 会話をしまう SQLite のファイル | `ohanashi.db` |
| `--screen フォルダ` | 画面のファイルのフォルダ | `画面` |
| `--searxng URL` | ウェブ検索に使う SearXNG | 環境変数 `SEARXNG_URL`、なければ使わない |
| `--sandbox-image イメージ` | 砂場のコンテナのイメージ | `ohanashi-sandbox`(手元にあれば。なければ `python:3.12-slim`) |
| `--sandbox-network ネットワーク` | 砂場のコンテナの `--network` | `none`(外につながらない) |
| `--work フォルダ` | 砂場と共有する作業フォルダの親 | `作業` |
| `--web-search URL` | ウェブ検索の API | `https://ollama.com/api/web_search` |
| `--control フォルダ` | 起動.sh と話すフォルダ(起動.sh が付けます) | なし(画面から再起動できない) |
| `--revision 版` | 画面に出す版(起動.sh がコミットを付けます) | なし |
| `--github-repos 一覧` | 会話に足してよい GitHub のリポジトリを絞る(`owner/名前` か `owner/*` を「,」で区切る) | なし(鍵で使えるものはどれでも足せる) |
| `--github-token 鍵` | GitHub の鍵(個人アクセストークン) | 環境変数 `GITHUB_TOKEN`、なければ鍵なし(公開のリポジトリだけ、1時間に60回まで) |
| `--github-api URL` | GitHub の API の基点(GitHub Enterprise なら `https://主機/api/v3`) | `https://api.github.com` |
| `--github-git URL` | clone・push する URL の頭(`URL/owner/名前.git` を使う) | API の基点から決める(`https://github.com` など) |
| `--git-author "名前 <メール>"` | 砂場の clone で commit するときの名前 | 鍵の持ち主の名前と `名前@users.noreply.github.com` |
| `--research-model モデル` | モデル帳を調べるモデル | 前に調べたモデル → 最近の会話のモデル → 道具を使える一番大きいモデル |
| `--research-max-size GB` | 調べるモデルの大きさの上限(GB。指名したモデルには効かない) | なし |
| `--no-research` | モデル帳を調べない(大きさ・能力だけ記録する) | 調べる(ウェブ検索が使えるとき) |

### 起動.sh で動かす(画面から再起動・新しいコミットで更新)

```sh
./起動.sh                          # kumu 作る をしてから動かす
./起動.sh --watch 60 -- --port 9000 # 60 秒ごとに新しいコミットを見る。-- の後ろはアプリの引数
```

`起動.sh` で動かすと、画面の ⚙ に版と「🔄 最新にして再起動」が出ます。押すと、`git pull --ff-only` → `kumu 作る` → アプリを動かし直す、をして、画面を読み直します。

`--watch 秒` を付けると、その秒ごとに `git fetch` して、追っている枝(`main` など)に新しいコミットがあれば同じように更新します。PR をマージすると、しばらくして手元のアプリが新しくなります(かんたんな CD)。

作り直しに失敗したとき(`git pull` できない・`kumu 作る` が通らない)は、前のアプリを動かしたままにして、画面の ⚙ と端末に理由を出します。失敗したコミットは、次の新しいコミットが来るまで試し直しません。`起動.sh` そのものの変更は、`起動.sh` を動かし直したときに効きます。Ctrl-C でアプリといっしょに止まります。

**注意:** 画面を開ける人は、だれでも再起動を頼めます(手元の枝を最新にして作り直すだけで、ほかのコードは動かせません)。

### ほかの機械から https で開く(Tailscale Serve)

スマホなどほかの機械から開くときは、[Tailscale](https://tailscale.com/) の [Serve](https://tailscale.com/kb/1312/serve) を前に置くと、`https://機械の名前.tailnet名.ts.net/` で開けます。https で開くと、ブラウザの通知など安全な場所(secure context)でしか使えないものも使えます。Tailscale につないだ機械からだけ開けて、証明書は Tailscale が用意します。

1. [管理画面の DNS](https://login.tailscale.com/admin/dns) で、**MagicDNS** と **HTTPS Certificates** を入れる
2. ohanashi-ollama は、いつもどおり起動する(`--listen` は既定の 127.0.0.1 のままでかまいません)
3. 同じ機械で `tailscale serve --bg 8080` と打つ(`--port` を変えたときはその番号)。出てきた `https://…ts.net/` を、Tailscale につないだスマホなどで開く

止めるときは `tailscale serve --https=443 off` です。今の設定は `tailscale serve status` で見られます。

**注意:** HTTPS の証明書を作ると、機械の名前と tailnet の名前が証明書の公開記録(Certificate Transparency)に載ります。会話の中身は外からは見えません。

### モードとモデル帳

見出しの「💬 会話」を押すと「🛠 コーディング」に切り替わります(もう一度押すと戻ります)。新しい会話は、前に選んだモードで始まります。

- **コーディング**: 場面を「🛠 コーディングモードのとき」にした決まり(はじめから入っている「コードを書くときの決まり」はこれです)が付き、「💻 砂場」が押されます。砂場か GitHub を使わなくても、作業フォルダのリポジトリの `OHANASHI.md` などを読みます
- **会話**: 場面が「💬 会話モードのとき」の決まりが付きます

⚙ の「🧠 モデル帳」に、Ollama のモデルの大きさ・パラメータの数・量子化・文脈の長さ・能力(🔧 道具・👁 画像)と、調べた特徴と点数(0〜5)が出ます。

1. 起動すると、別のスレッドで Ollama のモデルを帳に記録します(`digest` が変わったモデルだけ聞き直します)
2. ウェブ検索(`--searxng` か `OLLAMA_API_KEY`)が使えれば、まだ調べていないモデルを、調べ役のモデルに調べさせます。モデルの名前でウェブを検索し、結果を読ませて、JSON の形(特徴・点数・注意)で答えさせます
3. 調べ役が小さい(7B 未満)か、半分以上調べられなかったときは、道具を使える2倍以上大きなモデルで1回だけ調べ直します
4. 新しい会話のモデルは、モードの点数(コーディングは道具を使えるモデルから)、日本語、小ささの順で選びます。見出しのモデルを選び直せば、そちらを使います

調べた中身は「直す」で手で直せます。手で直したモデルは、調べ直しても書きかえません(「手直しをやめる」で戻せます)。「調べ直す」「みな調べ直す」でもう一度調べさせます。

```sh
./出力/ohanashi-ollama --searxng http://localhost:8888 --research-model qwen3:30b --research-max-size 24
```

### 決まりを付ける

⚙ の「📜 決まり」で、モデルに守ってほしいことを書いた決まりを作り、会話に付けます。Claude Code の `CLAUDE.md` のようなものです。

1. ⚙ を開いて「決まりを作る・直す」を押し、名前と中身(Markdown で書けます)を書いて保存する。最初から「コードを書くときの決まり」の見本が1つ入っています
2. 決まりの一覧で、この会話に付けるものに印を付ける。印は会話ごとに覚えます。「付ける場面」を「いつも」にした決まりは新しい会話にはじめから、「🛠 コーディングモードのとき」にした決まりはコーディングモードにしたときに印が付きます(会話モードに戻すと外れます)
3. 送ると、付けた決まりを、会話の指示の前に見出し(`# 決まり: 名前`)を付けてモデルに渡します

決まりを直すと、付けているすべての会話の、次の答えから新しい中身を使います。⚙ のボタンの横の「📜2」は、付けている決まりの数です。決まりは答えるたびにモデルの文脈を使うので、付けた決まりの合計が長い(6000 文字を超える)ときは、⚙ に知らせを出します。

リポジトリの決まりは、ファイルに書いておけます。「💻 砂場」か「🐙 GitHub」を押して送ると、`作業/会話の番号/` と、その1つ下のフォルダのうち git のリポジトリ(`.git` があるもの)で、`OHANASHI.md` → `AGENTS.md` → `CLAUDE.md` の順に探し、最初に見つかった1つを「リポジトリ 名前 の決まり」として渡します。ほかの道具向けに `AGENTS.md`・`CLAUDE.md` を書いてあるリポジトリでは、そのまま効きます。ohanashi のモデルにだけ伝えたいことは `OHANASHI.md` に書きます。たとえば:

```markdown
- 試験は `kumu 試験` で動かし、通ってから push する
- コメントと commit の文は日本語で書く
- 新しい機能の説明は README の「決めたこと」に、その機能の節を作って書く
```

答えの途中で `github_clone` や `run` の `git clone` で clone したときも、道具を使ったあとに探し直して、見つかればモデルに渡します。読んだときは、答えの上に「リポジトリの決まりを読みました: r/OHANASHI.md」と出します(スレッドの最初の答えと、答えの途中で見つけたときだけ)。

### 画像と PDF を添える

画面にファイルを落とすか、入力欄に貼るか(Ctrl+V・⌘V)、入力欄の左の 📎 で選ぶと、入力欄の上に並びます。✕ で外せます。書いて送ると、問いといっしょに送ります(添えるだけで、書かずに送ることもできます)。

- **画像**(PNG・JPEG・WebP・GIF など、ブラウザが読めるもの)は、長い辺 1600px までに縮めて JPEG(透明があれば PNG)にしてから送ります。1つの問いに 8 枚まで。読めるのは、画像を扱えるモデル(`ollama pull qwen2.5vl` や `gemma3` など)だけです。モデルの一覧では、画像を読めるモデルに 👁 が付きます。画像を読めないモデルの会話で画像を添えると、送るボタンを押せなくなり、画像を読めるモデルの名前が出ます(押すと、その会話のモデルが変わります)
- **PDF** は、ブラウザでページごとに文を取り出して(「--- 3 ページ ---」で区切る)送ります。20MB まで。スキャンした PDF のように文字のないページは、札に「🖼 2 ページは文字がありません。画像にして送る」と出て、印が付いていればそのページを画像にして「報告.pdf の 2 ページ」として添えます(画像と合わせて 8 枚まで。印を外すと文だけ送ります)
- **文字のファイル**(`.txt`・`.md`・`.csv`・`.json`・コードなど)は、そのまま送ります。5MB まで
- 添える文は、1つの問いで合わせて 10 万字まで。8000 字を超えると、モデルの文脈に入りきらないかもしれないと知らせます

送った問いの下には、画像を小さく、PDF などを「📄 報告.pdf(12 ページ・3.4 万字)」の札で出します。押すと、画像そのものや取り出した文を開けます。添えたものは会話帳にしまい、そのスレッドで続けて聞いても、毎回モデルに送り直します(Ollama は前の画像を覚えていないため)。

### ウェブで調べる

ウェブ検索には、自分で動かす [SearXNG](https://docs.searxng.org/) か、[Ollama の web 検索 API](https://docs.ollama.com/capabilities/web-search) を使います。両方あれば SearXNG を使います。どちらもないと「🌐 ウェブ」のボタンは押せません。

**SearXNG**(アカウントもキーも要りません)。Docker なら次のように動かします。

```sh
mkdir -p searxng
docker run -d --name searxng -p 8888:8080 -v "$PWD/searxng:/etc/searxng" searxng/searxng
```

最初に起動すると `searxng/settings.yml` ができます。JSON で答えるのを許すように、ファイルの終わりに次を足して(足さないと JSON の要求は 403 で断られます)、`docker restart searxng` します。`server:` に `limiter: true` があれば `false` にします。

```yaml
search:
  formats:
    - html
    - json
```

`curl 'http://localhost:8888/search?q=test&format=json'` で JSON が返れば準備はできています。そのあと SearXNG の URL を渡して起動します。

```sh
SEARXNG_URL=http://localhost:8888 kumu 実行
```

**Ollama の web 検索 API**。ollama.com にサインインして [API キー](https://ollama.com/settings/keys)を作り、環境変数 `OLLAMA_API_KEY` に入れて起動します。

```sh
OLLAMA_API_KEY=キー kumu 実行
```

起動すると「ウェブ検索: SearXNG(…)を使います。」のように、何で調べるかを出します。SearXNG は起動したときに1回聞いてみて、使えなければ理由を出します。

調べた言葉(最後の問い)は SearXNG から検索サービスへ、または ollama.com へ送られます。ローカルの外に出したくない問いでは、ボタンを押さないでください。

### 砂場でコードを動かす

[Docker](https://www.docker.com/products/docker-desktop/) を動かしておくと、入力欄の横の「💻 砂場」を押せます。押して送ると、モデルに2つの道具を渡します。

- `run`: シェルのコマンドを動かす(1つ 120 秒まで)
- `write_file`: ファイルを書く

モデルが道具を呼ぶと、会話ごとのコンテナ(`ohanashi-ポート-会話の番号`)の中で行い、結果をモデルに返して続きを答えてもらいます(1つの答えで 30 回まで)。書いたファイルとコマンドの出力は、答えの中にそのまま出ます。コンテナの `/work` は手元の `作業/会話の番号` と同じフォルダなので、できたファイルを手元で開けます。

道具を使えるモデル(qwen3 など)で使ってください。はじめて使うときはイメージを取ってくるので、先に `docker pull python:3.12-slim` しておくと待たずに済みます。コンテナは、はじめは外のネットワークにつながらないので、`pip install` や `apt-get install` はできません。使いたい会話では、⚙ の設定の「💻 砂場からインターネットにつなぐ」に印を付けます。次に砂場を使うときに、コンテナを `--network bridge` で作り直します(作業フォルダのファイルは残りますが、それまでに入れたものは消えます)。すべての会話でつなぎたいときは `--sandbox-network bridge` を付けて起動します。ほかの言語を使うなら `--sandbox-image node:22` のようにイメージを変えます。

コンテナは会話を消すと消えます(作業フォルダは残ります)。モデルが動かすコマンドは確かめずに行うので、作業フォルダに大事なファイルを置かないでください。

答えの中で作業フォルダにファイルができたり変わったりすると、答えの終わりに「📄 報告.docx(24KB)」のようなリンクが出ます。押すと落とせます(PDF と画像はブラウザで開きます)。前にできたファイルも、⚙ の設定の「📁 作業フォルダ」から落とせます。

#### Word・PDF の文書を作る

文書を作れる砂場のイメージ `ohanashi-sandbox` を作っておくと、モデルに道具 `make_document` も渡します。「今の話を Word の報告にまとめて」「PDF にして」と頼むと、モデルが Markdown で中身を書き、砂場の中で Word(docx)か PDF にします。できたファイルは答えの終わりのリンクから落とせます。

```sh
docker build -t ohanashi-sandbox 砂場    # 目安 1GB ほど。作ったら起動し直す
```

イメージは `python:3.12-slim`(Debian bookworm)に、pandoc・WeasyPrint・python-docx・openpyxl・matplotlib と日本語のフォント(Noto CJK)を足したものです([砂場/Dockerfile](砂場/Dockerfile))。`--sandbox-image` を付けずに起動すると、`ohanashi-sandbox` があればそれを使い、「砂場: ohanashi-sandbox で、Word・PDF の文書を作れます」と出します。なければ今までどおり `python:3.12-slim` を使い、`make_document` は渡しません。[起動.sh](起動.sh) は、`砂場/` が変わったときにイメージを作り直します(Docker がなければ飛ばします)。表や図の凝った文書は、モデルが `run` で python(python-docx・openpyxl・matplotlib)を書いて作ることもできます。

モデルが道具を使わずに「報告.docx を作成しました」と書いたときは、一度だけ道具で作るように頼み直し、それでもできなければ「⚠ ファイルはできていません」と出します。

### GitHub のリポジトリを読む

GitHub の鍵を環境変数 `GITHUB_TOKEN` に入れて起動します(環境変数で渡すと、`ps` に出ません)。

```sh
GITHUB_TOKEN=github_pat_… kumu 実行
```

起動すると「GitHub: 名前 としてつながりました。」と出ます(鍵が違えば「注意: GitHub の鍵を確かめられませんでした(…)」)。リポジトリは、動かしている間に画面の ⚙ の設定の「GitHub のリポジトリ」で、会話ごとに足したり外したりします。それぞれ「読むだけ」か「読み書き」を選びます。足すときは、鍵で使えるリポジトリが候補に出ます(`owner/名前` を書けば、候補にないものも足せます)。

足せるリポジトリを絞りたいときは、`--github-repos suru-lang/suru,suru-lang/*` のように起動します(鍵がなくても、ここに書いた公開のリポジトリは読めます)。入力欄の横の「🐙 GitHub」を押して送ると、モデルに4つの道具を渡します。

- `github_repo`: リポジトリの設定(既定の枝・説明・トピック・ラベル)
- `github_tree`: ファイルの一覧(枝と、フォルダで絞れる。400 まで)
- `github_file`: ファイルの中身(20000 文字まで)
- `github_issues`: issue・PR の一覧(50 まで)か、1つの本文とコメント

画面には「🐙 o/r の README.md を読みました(2 行)」のように、何を読んだかだけを出します。読んだ中身はモデルにだけ渡し、答えといっしょには保存しません。

鍵は fine-grained の個人アクセストークンで、読むリポジトリに Metadata・Contents・Issues・Pull requests の読みの権限を付けてください。

### GitHub の issue を書く

会話の「読み書き」のリポジトリがあると、モデルに道具 `github_issue` も渡します。`action` で次のことをします。

- `create`: issue を作る(題・本文・ラベル)
- `update`: issue・PR の題・本文・ラベルを変える
- `comment`: issue・PR にコメントする
- `close`: issue を閉じる(完了か予定なし)
- `reopen`: 閉じた issue を開く

画面で確かめずに行います。書いたら「🐙 o/r に issue [#7](…) を作りました: 題」のように、リンクの1行を答えに残します。書いた本文とコメントの終わりには「— ohanashi-ollama(モデル名) で書きました」を付けます。「読むだけ」のリポジトリに書こうとしたときは、書かずにモデルへ理由を返します。

書くリポジトリの鍵には、Issues と Pull requests の読み書きの権限が要ります。

### GitHub のリポジトリを直して PR を作る

「🐙 GitHub」と「💻 砂場」を両方押して送ると、さらに2つの道具を渡します。

- `github_clone`: リポジトリを砂場の `/work/名前` に clone する(最新のコミットだけ)。手元では `作業/会話の番号/名前` です
- `github_push`: `/work/名前` で変えたものを全部 commit して、枝に push する(読み書きのリポジトリだけ)

モデルは clone したファイルを `run` と `write_file` で直して確かめ、`github_push` で `ohanashi/fix-typo` のような新しい枝に push し、`github_pr` で PR を作ります。git はサーバー(手元)で動かすので、コンテナに git や鍵がなくても、コンテナがネットワークにつながっていなくてもできます。commit の名前は鍵の持ち主の名前と `名前@users.noreply.github.com` で、`--git-author "名前 <メール>"` で変えられます。commit の文の終わりにも「— ohanashi-ollama(モデル名) で書きました」を付けます。

#### 頼み方のこつ

小さいモデルは、道具を呼ばずに「push しました」「PR を作りました」と書いたり、呼び出しを文で書いたりしがちです(qwen3-coder-next・qwen3.6:35b で見ました)。サーバーは push・PR の結果を確かめるようモデルに添え、できていないのに「できた」と書いたら2回まで頼み直しますが、次のように頼むのがいちばん確実です。

- 道具の名前・リポジトリ・枝を書く: 「github_push ツールを使って、ohanashi/add-c-hello-world ブランチに push してください」「github_pr ツールを使って、ohanashi/add-c-hello-world ブランチから main ブランチに対して PR を開いてください」
- clone → 直す → push → PR を、1回に1つずつ頼む
- 作業ごとに新しいスレッドにする(見出しの「＋ スレッド」。長いスレッドでは、前の失敗や作り話に引きずられます)。リポジトリの設定と、砂場に clone したものはそのまま使えます
- 本当に道具を使ったかは、途中経過の題(「途中経過(道具: github_push)」)か、起動した端末の `[会話 番号] 道具 …` の行で確かめる

#### 鍵の作り方

1. GitHub の [Settings → Developer settings → Personal access tokens → Fine-grained tokens](https://github.com/settings/personal-access-tokens/new) で「Generate new token」を押す
2. 「Repository access」で、会話で使うリポジトリだけを選ぶ
3. 「Permissions」の「Repository permissions」で、次を選ぶ
   - 読むだけ: Metadata(Read-only、いつも付きます)・Contents・Issues・Pull requests を Read-only
   - issue を書く: Issues を Read and write
   - push して PR を作る: Contents と Pull requests を Read and write
4. できた鍵(`github_pat_…`)を `GITHUB_TOKEN` に入れて起動する

**注意:** 画面は既定で 127.0.0.1 だけで待ち受けるので、同じ機械の中からだけ開けます。ほかの機械(スマホなど)から開くときは `--listen 0.0.0.0` で起動します。そのときは同じネットワークのだれでも会話を読めるので、信用できるネットワークだけで使ってください。Tailscale を使っているなら、[Tailscale Serve](#ほかの機械から-https-で開くtailscale-serve) で https から開くほうが安全です。ほかのサイトのページから会話を読み書きされないように、`Origin` の見出しが自分と違う要求は断ります。

## 試験

```sh
kumu 試験                   # 会話帳(SQLite)・Ollama の行の読み方・ウェブ検索・引数・GitHub の許し・決まりのまとめ方・作業フォルダのファイルの試験
node 道具/書式試験.js        # 画面の Markdown の変換の試験
node 道具/道試験.js          # 画面の道(#会話/スレッド)の試験
node 道具/頁試験.js          # PDF の文字のないページを画像にするところの試験
node 道具/通知試験.js        # 答えが終わったときの通知の中身とタブの題の印の試験
```

本物の LLM の代わりに、決まった答えを返す偽の Ollama([道具/偽Ollama.suru](道具/偽Ollama.suru))で、全部を動かして確かめられます。

```sh
suru 道具/偽Ollama.suru &                       # http://localhost:11435
kumu 実行 -- --ollama http://localhost:11435 --db 出力/試し.db
OLLAMA_API_KEY=試し鍵 kumu 実行 -- --ollama http://localhost:11435 --web-search http://localhost:11435/api/web_search   # ウェブ検索も試す
kumu 実行 -- --ollama http://localhost:11435 --searxng http://localhost:11435   # SearXNG で試す
```

偽の Ollama は、最後の発言に「おうむ返し: 」を付けて1文字ずつ返します。モデル「偽-考える」は先に考えを流し、「書式」を含む問いには Markdown の見本を返します。`/api/web_search` は、キーが `試し鍵` なら問いを題に入れた2つの結果を返し、`/search?q=…&format=json` は SearXNG のふりをして6つの結果を返します。検索の結果を受け取ったモデルは答えの終わりに「 [検索あり]」を付けます。GitHub の道具を渡されて「GitHub」を含む問いを受けると `o/r` の `README.md` を読み、「issue を作って」なら `o/r` に issue を作り、「issue を閉じて」なら `o/r` の #1 を閉じ、「clone して」「push して」「main に push して」「PR を作って」でそれぞれの道具を呼び、砂場の道具を渡されて「決まりを置いて」を受けると、`run` でリポジトリ `/work/q` と `OHANASHI.md` を作ります。指示(system)が届いていれば、答えの終わりに「 [指示: …]」と付けます。「発言の数」を含む問いには届いた問いの数(「 [問い 2]」)を付け、スレッドのまとめの問いには「まとめ: 発言 N 個」を返します。終わりの `prompt_eval_count` は、届いた発言の JSON の文字の数です。偽の Ollama は GitHub の API のふりもします(`--github-api http://localhost:11435`、鍵は `試し鍵`)。GitHub Actions では、これを相手に curl と Node の WebSocket で確かめています([.github/workflows/試験.yml](.github/workflows/試験.yml))。

### サーバーの道

| 道 | 答え |
|---|---|
| `GET /api/github/repos` | 会話に足すリポジトリの候補(鍵で使えるもの。`--github-repos` があればそれに入るものだけ) `{"repos":[…]}` |
| `GET /api/info` | Ollama の場所と版、ウェブ検索と砂場を使えるか `{"ollama":…,"version":…,"web":真偽,"sandbox":真偽,"documents":真偽(砂場で文書を作れるか),"github":真偽,"githubRepos":[…],"githubUser":…}` |
| `GET /api/models` | 入っているモデルの名前と、モデル帳とおすすめ `{"models":[…],"catalog":[{"name":…,"capabilities":["completion","vision",…],"size":バイト,"family":…,"params":10億の数,"quantization":…,"context":…,"summary":…,"scores":{"coding":…,"chat":…,"japanese":…,"reasoning":…}かnull,"notes":…,"researcher":…,"researched":時刻,"failed":真偽,"manual":真偽},…],"recommended":{"会話":{"name":…,"reason":…},"コーディング":{…}}}` |
| `PUT /api/models` | モデル帳を手で直す `{"name":…,"summary":…,"scores":{…},"notes":…}`(`"manual":false` なら手直しをやめて、次に調べ直す) |
| `POST /api/models/research` | 調べ直す `{"name":…(省くと全部),"researcher":…(省くと選ぶ)}`。様子は `/api/info` の `"catalog":{"state":…,"done":…,"total":…,"researcher":…,"message":…}` |
| `GET /api/conversations` | 会話の一覧(新しく話した順。`"threads"` はスレッドの数) |
| `POST /api/search` | 題か発言に言葉を含むスレッド `{"q":…}` → `[{"id":会話,"thread":スレッド,"title":…,"threadTitle":…,"snippet":…}, …]` |
| `POST /api/conversations` | 会話を1つ目のスレッドといっしょに作る `{"model":…,"mode":"会話"か"コーディング","rules":[決まりの番号, …]}`(`rules` を省くと、既定の決まりとモードの場面の決まりを付ける。`model` を省くと、モデル帳のおすすめ) |
| `GET・PUT・DELETE /api/conversations/番号` | 会話の中身(設定と `"threads":[{"id":…,"title":…,"updated":…}]`)を読む・題とモデルと指示と温度と砂場のネットワーク(`"network":真偽`)と GitHub のリポジトリ(`"repos":[{"repo":…,"write":真偽}]`)とメモ(`"memo":…`、8000 文字まで)とモード(`"mode":…`、変えると場面の決まりを付け直す)と付ける決まり(`"rules":[決まりの番号, …]`、この順にまとめる)を変える・消す(スレッドと発言も消える) |
| `GET・POST /api/rules` | 決まりの一覧 `[{"id":…,"name":…,"default":真偽,"length":文字数,"updated":…,"uses":付けている会話の数,"scene":場面}, …]`・決まりを作る `{"name":…,"content":…,"scene":""か"いつも"か"会話"か"コーディング"}`(前の `"default":真偽` も使える)(名前は 100 文字、中身は 8000 文字まで) |
| `GET・PUT・DELETE /api/rules/番号` | 決まりの中身 `{"id":…,"name":…,"content":…,"default":真偽,"scene":…}` を読む・変える(本文にある項目だけ)・消す(付けている会話から外れる) |
| `GET /api/conversations/番号/files` | 砂場の作業フォルダ(`作業/会話の番号`)のファイルの一覧 `{"files":[{"path":…,"size":…,"modified":…,"dir":真偽}, …],"truncated":真偽}`(`.git` は除き、clone したリポジトリはフォルダの名前だけ。500 まで) |
| `GET /api/conversations/番号/files/道` | 作業フォルダのファイル(`Content-Disposition: attachment`。PDF と画像は `?view=1` で `inline`) |
| `GET・POST /api/conversations/番号/threads` | スレッドの一覧・スレッドを作る `{"title":…}`(省ける) |
| `GET・PUT・DELETE /api/threads/番号` | スレッドの中身 `{"id":…,"conversation":…,"title":…,"messages":[…]}` を読む・題を変える・消す(会話の最後のスレッドは消せない) |
| `POST /api/threads/番号/messages` | 発言を足す `{"role":"user"か"assistant","content":…}`。問いには `"attachments":[{"kind":"image","name":…,"type":"image/jpeg","data":"base64…"}, {"kind":"text","name":…,"type":…,"text":…,"pages":…}]` を添えられる。スレッドの中身の発言には、添えたものの目録 `"attachments":[{"id":…,"kind":…,"name":…,"type":…,"pages":…,"chars":…}]` が付く |
| `GET /api/attachments/番号` | 添えたもの。画像はそのファイル、文書は取り出した文(`text/plain`) |
| `DELETE /api/threads/番号/last-answer` | 最後の答えを消す(作り直すとき) |
| `POST /api/conversations/番号/messages`・`DELETE /api/conversations/番号/last-answer` | 前の版の道。会話の一番新しく作ったスレッドに発言を足す・最後の答えを消して、スレッドの中身を返す |
| `GET /ws`(WebSocket) | `{"thread":番号}` が届くたびに、そのスレッドの発言を会話の設定で Ollama へ送り、答えを流す(`{"conversation":番号}` だけなら、その会話の一番新しいスレッド)。`"summary":true` なら、スレッドのまとめを流す(しまわない)。`"web":true` も付いていれば、先にウェブで調べる。`"code":true` なら砂場の道具を、`"github":true` なら GitHub の道具を渡す |
| `POST /api/chat` | WebSocket を使えないときの同じもの(1行1つの JSON) |

流す答えは1つずつの JSON です: `{"content":…}`(答えの続き)、`{"thinking":…}`(考え)、`{"stats":{"tokens":…,"seconds":…,"prompt":送った文のトークンの数}}`、`{"error":…}`。ウェブで調べたときは、はじめに `{"sources":[{"title":…,"url":…}, …]}`(調べられなかったときは `{"notice":…}`)を送ります。砂場で道具を使ったときは、使う前に `{"running":…}`、使った後に `{"tool":{"name":"run","command":…,"output":…,"code":…}}` か `{"tool":{"name":"write_file","path":…,"content":…,"output":…}}`(`make_document` は `{"tool":{"name":"make_document","path":…,"format":…,"output":…}}`)を送ります。答えの中で作業フォルダにファイルができた・変わったときは、終わりに `{"files":[{"path":…,"size":…}, …]}` を送ります。GitHub の道具では `{"running":"🐙 …を読んでいます"}` と `{"tool":{"name":"github_file","summary":…}}` を送ります(中身は送りません)。WebSocket では最後に `{"done":true}` を送ります。

## 決めたこと

### 会話のしまい方

1. **会話はサーバーの SQLite にしまう。** 表は `会話`(番号・題・モデル・指示・温度・作成・更新)と `発言`(会話・役・内容・作成)です。時刻は UNIX 時間の秒です。温度が負ならモデルの既定の温度を使います。
2. **発言を保存するのは画面。** 画面は、問いを送る前に問いを、答えを受け取り終わったら(止めたときも、そこまでの)答えを保存します。サーバーは、答えを流すときに会話の発言をデータベースから読んで Ollama に送ります。答えが1文字も届かなかったときは、答えを保存しないので、「もう一度」で同じ問いを聞き直せます。
3. **題は最初の問いから。** 題が空の会話に最初の問いを足すと、その1行目のはじめの 40 文字を題にします。画面で題をクリックすると変えられます。
4. **考えは保存しない。** 考えるモデルの考え(`thinking`)は画面に出すだけで、次に送る発言には入れません(Ollama の勧めのとおり)。
5. **検索は LIKE で。** 題か発言の中身に言葉を含む会話を、新しく話した順に 100 まで返します。`%`・`_`・`\` はただの文字として探し、英字の大文字小文字は区別しません。最初に見つかった発言の、言葉のまわりを抜き出して一覧に出します。
6. **要求ごとにデータベースを開いて閉じる。** 答えを流している間はデータベースを開いたままにしません。同時の書き込みは `busy_timeout` で待ちます。

### スレッド

1. **会話の下にスレッドを置く。** Claude のプロジェクトのように、会話は設定(モデル・指示・温度・砂場のネットワーク・GitHub のリポジトリ)の入れ物にし、話題ごとにスレッドを作って話します。表 `スレッド`(番号・会話・題・作成・更新)を足し、`発言` に `スレッド` の列を足しました。設定は会話にあるので、新しいスレッドでもリポジトリなどを足し直さずに使えます。
2. **モデルに送るのはスレッドの発言だけ。** 会話の指示は今までどおり先頭に入れますが、ほかのスレッドの発言は送りません。長い会話は、送る文が長くなって答えはじめるまでが遅くなり、前の話題や失敗にも引きずられるためです。前の答えで push・PR をしたか(「push・PR のあとに確かめさせ、できていなければやり直させる」の項目など)も、そのスレッドの中で見ます。
3. **前の版の会話は1つ目のスレッドに移す。** 起動したときに、スレッドのない会話ごとにスレッドを1つ(題は会話の題)作り、スレッドの決まっていない発言をそこに付けます。何度起動しても、2回目からは何もしません。
4. **砂場と作業フォルダは会話ごと。** コンテナ(`ohanashi-ポート-会話の番号`)も `作業/会話の番号` も変えません。前のスレッドで clone したリポジトリを、次のスレッドで直して push できます。そのかわり、2つのスレッドで同時に砂場を使うと、同じコンテナを使います。
5. **前の道も残す。** `/api/conversations/番号/messages`・`/last-answer` と WebSocket の `{"conversation":番号}` は、その会話の一番新しく作ったスレッドのこととして動きます。開いたままの前の版の画面でも話せるようにするためです。
6. **題はスレッドごと。** スレッドに最初の問いを足すと、その1行目のはじめの 40 文字をスレッドの題にします(会話の題が空なら、会話の題にも)。
7. **会話の最後のスレッドは消せない。** スレッドのない会話を作らないように、最後の1つを消すときは会話ごと消します。
8. **画面の道は `#会話/スレッド`。** 読み込み直しても同じスレッドを開きます。前の版の `#会話` のリンクは、その会話の一番新しく話したスレッドを開きます。道の読み書きは `画面/道.js` にまとめ、`node 道具/道試験.js` で確かめます。
9. **一覧は開いている会話の下にスレッドを並べる。** スレッドが2つ以上あるときだけ、開いている会話の下に、新しく話した順に並べます。ほかの会話はたたんだまま、スレッドの数だけを出します。会話を探したときは、見つかったスレッドを「会話の題 › スレッドの題」で並べます。
10. **見出しの題は2つ。** 大きいほうがスレッドの題、その前の小さいほうが会話の題で、どちらも押すと変えられます。会話の中身(`GET /api/conversations/番号`)は設定とスレッドの一覧だけを返し、発言はスレッドの中身で読みます。
11. **答えはそのスレッドにしまう。** 答えを受け取っている間にほかのスレッドを開くと、今までと同じく答えを止めますが、そこまでの答えは頼んだスレッドにしまいます。
12. **会話のメモで次のスレッドへ持ち越す。** 会話に `メモ`(8000 文字まで)の列を足し、送るときに会話の指示のあとへ「## これまでのスレッドで分かったこと」として足します。ほかのスレッドの発言を送らないかわりに、決めたこと(枝の名前・試験の動かし方など)を短く渡すためです。指示(どう答えるか)と分けたのは、答えから足した文が人の書いた指示を書きかえないようにするためです。
13. **「メモに足す」は答えだけを足す。** 答えの「メモに足す」は、途中経過(考えと道具の跡)を除いた答えをメモの終わりに足して保存し、⚙ を開いて見せます。8000 文字を超えたら保存せず、短くするよう知らせます。
14. **長くなったら新しいスレッドを勧める。** Ollama が答えの終わりに返す、送った文のトークンの数(`prompt_eval_count`。`stats` の `prompt`)が 4096(文脈の目安 8192 の半分)を超えたら、答えの下に「このスレッドは長くなりました」と「まとめて新しいスレッドへ」を出します。8192 を超えたら、前の発言が読まれていないおそれがあると出します。モデルごとの文脈の長さはまだ分からないので、多くのモデルで使える 8192 を目安にしました。閉じると、そのスレッドでは出しません。
15. **まとめは流して、しまわない。** WebSocket に `{"thread":番号,"summary":true}` を送ると、スレッドの発言(道具の跡を除く)のあとに「次のスレッドに引き継ぐためにまとめて」という問いを足して、道具なしで答えを流します。長いスレッドは、はじめの 4 個と終わりの 30 個の発言だけを送ります。画面はまとめを直せる欄に出し、「新しいスレッドの頭に置く」(「題 の続き」のスレッドの最初の発言にする)か「メモに足して新しいスレッドへ」を選べます。もとのスレッドには何も足しません。答えをまとめるのに時間がかかるので、別の道で待たせずに、ふだんの答えと同じく流すことにしました。

### 画面

1. **画面は1つのページ。** 開いている会話は道の `#番号` で、読み込み直しても同じ会話を開きます。
2. **Markdown は自前の小さな変換で。** 外のライブラリを読まないので、ネットワークにつながっていなくても動きます。先に全部の文字を HTML として逃がしてから書式を付けるので、答えに HTML があっても文字のまま出ます。リンクは http と https だけです。
3. **変換を確定する Enter では送らない。** Chrome は確定の Enter に `isComposing` を付けますが、Safari は先に `compositionend` を出してから `isComposing` のない keydown を出します。`isComposing`・keyCode 229・`compositionend` から 150 ミリ秒の間の Enter は、確定とみなして送りません(macOS の Safari と ATOK で、確定の Enter で送られてしまったため)。
4. **止めるときは WebSocket を閉じる。** サーバーは次に送るところで失敗して、Ollama への接続も閉じます(Ollama も答えを作るのをやめます)。次に送るときにつなぎ直します。
5. **途中経過はたたんで出す。** 考えと、道具を使った跡(`~~~~` で囲んだコマンドの出力・書いたファイル、「📝 」「🐙 」で始まる行)と、その間のモデルの文を、はじめは閉じた「途中経過」の欄に入れ、最後の道具の跡より後の答えだけを開いて出します。保存した答えには印を足さず、読み込んだ会話でも同じ形を見分けて分けます(`書式.js` の `途中を分ける`)。答えを受け取っている間は、欄の題に今していること(「💻 動かしています: …」など)を出します。会話を探して見つかった所が途中経過の中なら、欄を開きます。
6. **道具の跡には見えない印を付ける。** 道具を使った跡の後に、見えない字(U+2063)で始まる「道具:名前」の行を足して保存し、途中経過はこの印で分けて、欄の題に使った道具の名前(「途中経過(道具: github_pr)」)を出します。モデルの文からはこの字を除きます。モデルが「🐙 … PR を作りました」のような道具の跡に似た文を書くと、道具を使ったように見えてしまったためです。印のない前の答えは、5 の形で分けます。モデルの文の ``` が閉じていないときは、道具の跡の前で閉じます。

### ウェブ検索

1. **Ollama の web 検索 API を使う。** 検索のサービスは、Ollama を使う人が一番キーを用意しやすいものにしました。`POST https://ollama.com/api/web_search` に `Authorization: Bearer キー` を付けて `{"query":…,"max_results":5}` を送ります。http ライブラリの HTTPS(OpenSSL)で、証明書と名前を確かめてつなぎます。
2. **調べるのは最後の問いそのまま。** モデルに検索の言葉を作らせる(道具の呼び出し)と、道具を使えるモデルでしか動かず、1回の答えに2回モデルを動かすので、まずは問いをそのまま送ります。
3. **結果は問いのすぐ前に指示(system)として渡す。** 「[1] 題・URL・中身(1500 文字まで)」を並べ、番号で出典を示すように頼みます。この指示は保存しないので、次の問いのときには渡しません(そのときボタンが押してあれば、また調べます)。
4. **出典は答えといっしょに保存する。** 画面は `sources` を受け取ったら、答えの終わりに「出典」の番号付きの一覧(Markdown のリンク)を足して、その全体を保存します。読み込み直しても出典が残り、次の問いのときにはモデルにも見えます。
5. **調べられなくても答える。** キーがない・違う・つながらないときは `{"notice":…}` を送って、検索なしで答えます。画面は答えの上に知らせを出します。
6. **ボタンの状態はブラウザが覚える。** 会話ごとではなく、`localStorage` に1つだけ覚えます。
7. **SearXNG も使える。** ollama.com につながらない・アカウントを作りたくないときのために、自分で動かす SearXNG の JSON の API(`GET /search?q=…&format=json`)も使えるようにしました。問いは UTF-8 のバイトごとに `%XX` にして送り、結果のはじめの5つを使います。結果の形(`results` の `title`・`url`・`content`)は Ollama の API と同じなので、そのあとは同じに扱います。`SEARXNG_URL` があれば、Ollama のキーより先に使います。

### 砂場

1. **会話ごとに1つのコンテナ。** 最初に砂場を使うときに `docker run -d … sleep infinity` で作り、そのあとは `docker exec` でコマンドを動かします。同じ会話の中では、前に書いたファイルや入れたものが残ります。サーバーを起動し直しても、コンテナが動いていればそのまま使います。
2. **外につながらない・使いすぎない。** 既定は `--network none` で、`--memory 2g --cpus 2 --pids-limit 512 --security-opt no-new-privileges` を付けます。1つのコマンドは `timeout 120` で止めます。モデルに返す出力は 8000 文字まで(長ければはじめと終わりの 4000 文字ずつ)です。
3. **道具は2つだけ。** `run`(sh -c)と `write_file` です。ファイルを読むのは `run` で `cat` できるので、道具を少なくしてモデルが迷わないようにしました。
4. **道具のくり返しはサーバーで。** モデルが `tool_calls` を返したら、サーバーが順に行い、`role: "assistant"`(呼び出し)と `role: "tool"`(結果)の発言を足して、もう一度 `/api/chat` に送ります。道具を呼ばなくなるか、30 回になるまでくり返します(はじめは 10 回でしたが、clone・変更・確認・push・PR と続けると届いてしまったため)。上限で止めたときは、「続けて」と送れば続きをします。
5. **使った跡は答えといっしょに保存する。** 画面は `tool` を受け取ったら、書いたファイルとコマンドの出力を Markdown のコードの塊(`~~~~` で囲む)として答えに足し、その全体を保存します。次の問いのときには、モデルにも前に動かしたことが見えます。途中の `tool` の発言そのものは保存しません。
6. **「プロセス」を使わない。** 標準の「プロセス」と「ファイル」(http ライブラリが読み込む)が C の `fread` を違う型で宣言していて、いっしょに読み込めません。そのため砂場は `system` と一時ファイルでコマンドを動かします。
7. **ネットワークは会話ごとに選ぶ。** 会話の `network` が真なら `bridge`、偽なら `--sandbox-network` の値(既定 `none`)でコンテナを作ります。コンテナが動いていても、`docker inspect` で見たネットワークが違えば作り直します。会話帳の表に `網` の列がない(前の版で作った)ときは、起動したときに `ALTER TABLE` で足します。

### 起動.sh

1. **再起動はシェルスクリプトで。** する のアプリは自分を作り直せないので、外の `起動.sh` が `git pull`・`kumu 作る`・動かし直しをします。macOS と Linux の `sh` で動きます。
2. **ファイルで話す。** アプリは `POST /api/restart` で `出力/制御/再起動` のファイルを置くだけです。`起動.sh` は2秒ごとにそれを見ます。様子は `起動.sh` が `出力/制御/状態` に書き、アプリは `/api/info` の `update` で画面に渡します。
3. **作れてから止める。** 新しいアプリが作れたときだけ、前のアプリを止めて動かし直します。止まっている間は数秒です。
4. **動かし直したかは時刻で知る。** `/api/info` の `started`(動き始めた時刻)が変わったら、画面を読み直します。

### GitHub

1. **API は suru-lang/github で。** GitHub の API を使うところは、ほかのアプリでも使えるように [suru-lang/github](https://github.com/suru-lang/github) に分けました。このアプリには、モデルの道具と、会話のリポジトリの許しだけを置きます。
2. **リポジトリは鍵と会話で絞る。** どのリポジトリに届くかは、まず鍵の権限で決まります(fine-grained の鍵なら、選んだリポジトリだけ)。そのうえで、会話ごとに使うものを、動かしている間に画面で足します。起動のときに決めた一覧だけでは、使うたびに起動し直すことになるためです。もっと絞りたいときは `--github-repos` を付けます。サーバーは会話を保存するときに `--github-repos` に合わないものを除き、道具を行うときにも、会話にないリポジトリなら断ってモデルに理由を返します。英字の大文字小文字は区別しません。
3. **Read と Write は会話ごと・リポジトリごと。** Claude のように、会話にリポジトリを足すときに「読むだけ」か「読み書き」を選びます。会話帳の `倉` の列に `[{"repo":…,"write":真偽}]` の JSON でしまいます(前の版の表には、起動したときに `ALTER TABLE` で足します)。
4. **読むのは確かめずに行う。** 読む道具は、画面で確かめずに行います。
5. **中身は保存しない。** 読んだファイルや issue は長く、リポジトリはあとで変わるので、モデルに渡すだけにします。画面には何を読んだかの1行だけを出し、それを答えといっしょに保存します。
6. **鍵は出さない。** 鍵は起動の記録にも画面にも出しません。`/api/info` は、鍵の持ち主の名前(`githubUser`)だけを返します。
7. **書くのも確かめずに行う。** 確かめずに書いてよいかは、リポジトリを足すときの「読み書き」で決めます。書くたびに画面で「やる・やめる」を聞く仕組みは作りませんでした。書く道具 `github_issue` は、読み書きのリポジトリが1つでもあるときだけ渡し、行うときにもそのリポジトリが読み書きかを確かめます。
8. **書く道具は1つ。** issue の作る・直す・コメント・閉じる・開くを、`action` で選ぶ1つの道具にしました。道具が多いと、小さいモデルが迷うためです。
9. **issue は消さない。** 消す道具は作らず、閉じる(`not_planned`)で足ります。GitHub でも、issue を消せるのはリポジトリの管理者だけです。
10. **書いたことがわかるようにする。** 書いた本文とコメントの終わりに「— ohanashi-ollama(モデル名) で書きました」を付けます(もう付いていれば付けません)。GitHub では鍵の持ち主が書いたことになるので、読む人がモデルの書いたものと見分けられるようにしました。
11. **git はサーバーで動かす。** clone・commit・push は、コンテナではなく手元の git で行います。鍵をコンテナに入れずに済み、git のないイメージやネットワークのないコンテナでも使えます。モデルはコンテナの中で、ファイルを直して確かめることだけをします。
12. **鍵は git のその時だけ渡す。** 鍵は、コンテナからは見えない `作業/.鍵`(700)に置いたファイルに書き、git を動かす sh がそれを読んですぐ消してから、`GIT_CONFIG_COUNT` などの環境変数で `http.extraHeader`(`Authorization: Basic …`)にします。コマンドの文字列(`ps` に出る)・`.git/config`・remote の URL には入れません。
13. **push は新しい枝だけ。** `github_push` は、リポジトリの既定の枝への push を断り(空のリポジトリのはじめの commit だけは既定の枝に push できます)、`--force` もしません(先へ進めない push は GitHub が断ります)。枝の名前は英数字と `- _ . /` だけにし、コマンドに渡すときは `'…'` で囲みます。保護された枝は GitHub が断ります。
14. **commit は変えたもの全部。** `github_push` は `git add -A` で全部を commit します。変えたものも、まだ push していない commit もなければ、push せずにそう返します。リポジトリの hook は動かしません(`core.hooksPath=/dev/null`)。
15. **コンテナの中の git push は、サーバーが代わりに行う。** コンテナには鍵がないので、モデルが `run` で `git push` しようとしたら、コンテナでは動かさずに、`/work` の中の clone(remote が会話のリポジトリのもの)を探して、`github_push` と同じことをサーバーで行います。枝は `git push origin 枝` の枝、なければ今の枝です。push する先は remote ではなく会話のリポジトリの URL なので、コンテナの中で remote を変えられても、鍵がほかへ送られることはありません。会話にリポジトリがないときは、動かさずに `github_clone`・`github_push` の使い方を返します(小さいモデルは、道具を渡しても `git push` をくり返したため)。
16. **作っていない PR を作ったと書いたら知らせる。** 答えに「PR #」「Pull Request #」「/pull/」「プルリクエスト」があるのに、その答えの中で `github_pr` が PR を作れていなければ、答えの後に「⚠ … PR を作れていません」という知らせを出します。小さいモデルは、道具を使わずに、または道具が失敗しても、PR を作ったと書くことがあったためです。
17. **push も同じように知らせる。** 答えに「push しました」「Pushed」などがあるのに、その答えの中で `github_push`(か `run` の `git push`)が push できていなければ、「⚠ … push していません」と知らせます。
18. **前の答えの道具の跡はモデルに送らない。** 画面が答えに足した道具の跡(`~~~~` で囲んだ塊、「🐙 」「📝 」で始まる行、道具の印の行)は、次にモデルへ送るときに除きます。送ると、モデルが道具を使わずに「🐙 … に push しました(…)」と同じ形の文を書くようになったためです。
19. **使った道具を端末に出す。** モデルが道具を使うたびに、起動した端末に「[会話 番号] 道具 名前: 引数 → 結果の頭」を1行出します。道具を本当に使ったかを、画面とは別に確かめられます。
20. **道具を使わずに「できた」と書いたら、頼み直す。** 会話に GitHub のリポジトリがあり、モデルが道具を1回も使わずに PR や push を「した」と書いたら、「書いただけでは何も起きない。github_push・github_pr を呼んで」とモデルに頼み直し、答えを続けてもらいます(画面には「⚠ … 頼み直しています…」と出します)。頼み直しは1つの答えで2回まで(下の「push・PR のあとに確かめさせ、できていなければやり直させる」の項目)で、それでもできていなければ 16・17 の知らせを出します。qwen3-coder-next では、何度か頼むと道具を使ったためです。
21. **前の答えでできたことは、また書いても知らせない。** 前の答え(画面が道具の印を付けたもの)で `github_push` が push できていた・`github_pr` が PR を作れていたなら、モデルがそれをまた書いても、知らせも頼み直しもしません。
22. **clone し直せる。** `github_clone` に `fresh: true` を付けると、もうある `/work/名前` を `/work/名前.old-時刻` に移してから clone し直します。`github_pr` が「no history in common」(枝の履歴が base とつながっていない)で断られたときは、clone し直して、変えたファイルを移し、新しい枝に push するようモデルに添えます。コンテナの中で `git init` したフォルダから push した枝は、GitHub の main とつながらず PR を作れなかったためです。
23. **道具の呼び出しを文で書いたときも頼み直す。** 道具を1回も使わずに、答えに道具の名前(`github_push`・`write_file`・`run "…"` など)と引数らしい書き方(`repo=`・`path=` など)の両方を書いたら、20 と同じように頼み直します。頼み直しの文には「説明していただけなら、道具の呼び出しを書かずに答え直して」と添えます。qwen3.6:35b が、道具を呼ぶ代わりに「github_push repo=…, branch=…」と手順を文で書いたためです。
24. **push・PR のあとに確かめさせ、できていなければやり直させる。** `github_push`(と `run` の `git push`)・`github_pr` の結果には、モデルだけに見える英語の指示を添えます。できたときは「答える前に `github_tree`(枝を指定)・`github_issues`(PR の番号)で確かめて」、断られたときは「エラーを読んで直し、もう一度呼んで。できたとは書かないで」です。`run` の `git commit` には「`git status`・`git log` で確かめて」を添えます。それでもモデルが、この答えの中でできていない push や PR を「できた」と書いたら、「道具の結果ではできていない。確かめて、もう一度呼んで」と頼み直します(画面には「⚠ モデルが『できた』と書きましたが、…やり直すように頼んでいます…」)。頼み直しは1つの答えで2回までです。qwen3.6:35b が、push や PR を失敗しても、そのまま「できた」と書いたり止まったりし、「github_push ツールを使って push してください」と頼み直すとできたためです。
25. **答えに書いた枝が GitHub にあるかを、サーバーが確かめる。** この答えでも前の答えでも push できていないのに、答えに「push した」「反映済み」などがあれば、「ブランチ」「branch」「枝」と同じ行に書いてある枝の名前らしいもの(「/」を含み、「.」を含まず、リポジトリの名前でないもの)を、読み書きのリポジトリの枝の一覧(GitHub の API)と比べます。ない枝があれば、画面に「⚠ 答えにある枝 … は GitHub にありません(サーバーが確かめました)」と出し、モデルにその枝がないことを伝えてやり直すように頼みます。GitHub に聞けなかったときは何も言いません。qwen3.6:35b が、push も `github_tree` もしていないのに「github_tree で確かめました。ブランチ … は GitHub 上に作成されています」と書いたためです。「push した」「プッシュした」「push 済」「反映済」も、push したと書いた言葉に足しました。
26. **頼み直しても呼び出しを文で書いたままなら、そう知らせる。** 2回頼み直しても、モデルが道具の呼び出しを文で書いただけで答えを終えたら、画面に「⚠ モデルは道具の呼び出しを文で書いただけで、道具は動いていません。答えにある実行結果やエラーは、モデルの作り話です」と出します。qwen3.6:35b が「github_push repo=…, branch=…」と書いたあとに「fatal: The remote end hung up unexpectedly」という作り話のエラーと、その原因の推測まで書いたためです。

### 決まり

1. **決まりはデータベースにしまう。** 会話帳に表 `決まり`(番号・名前・内容・既定・作成・更新)と `会話の決まり`(会話・決まり・順)を足しました。会話と同じファイルにまとまり、画面から直せます。`決まり/` のフォルダに Markdown のファイルで置く手もありましたが、実行ファイルとデータベースのファイルだけで動く今の形に合わせました。リポジトリに置きたい決まりは、`OHANASHI.md` に書けます。
2. **会話は決まりを番号で指す。** 写しを持たないので、決まりを直すと、付けている会話の次の答えから新しい中身を使います(`CLAUDE.md` を直したときと同じ)。前の答えは変わりません。決まりを消すと、付けていた会話からも外れます。
3. **決まりと指示を1つの system にまとめて、先頭に置く。** 送るときに「決まり(付けた順)→ リポジトリの決まり → 会話の指示(`# この会話の指示`)→ メモ」を見出し付きで1つの `system` の発言にします。モデルのテンプレートによっては、2つ目からの `system` を読まないためです。決まりを付けていない会話には、今までと同じ本文を送ります。スレッドのまとめにも決まりを渡します(リポジトリの決まりは渡しません)。
4. **今の指示はそのまま残す。** 会話ごとの指示は「この会話だけの指示」として使えます。
5. **見本を1つ入れる。** はじめて決まりの表を作ったときに、「コードを書くときの決まり」(今の書き方に合わせる・頼まれた所だけ変える・動かして確かめる・分からなければ聞く など)を1つ入れます。既定の印は付けないので、使う人が会話に付けます。消したあとにまた入れないように、入れたらデータベースの `user_version` を 1 にします。
6. **長さに限りを付ける。** 決まりは送るたびにモデルの文脈を使い、Ollama の文脈(`num_ctx`)は短いことが多いので、1つの決まりは 8000 文字までにしました。画面は付けている決まりの合計の文字数を出し、6000 文字を超えたら知らせます。
7. **リポジトリの決まりのファイルは、砂場か GitHub を使う答えで読む。** 作業フォルダ(`作業/会話の番号/`)そのものと、その1つ下のフォルダのうち `.git` があるものだけを見ます(深くは探しません)。`OHANASHI.md` → `AGENTS.md` → `CLAUDE.md` の順に最初の1つを、頭の 4000 文字まで読みます。長ければ切って、「続きは cat /work/…/OHANASHI.md で読んでください」と添えます。読むのは手元の sh なので、コンテナがなくても読めます。
8. **答えの途中で見つけたら、すぐ渡す。** 砂場の道具を使ったあとに探し直し、前と違えば「作業フォルダのリポジトリに、次の決まりがあります」という `system` の発言を道具の結果のあとに足します。clone してから直すまでを1つの答えで行うときにも、決まりに従えるようにしました。砂場の案内にも「決まりのファイルがあれば従ってください」と書きました。
9. **読んだことは、スレッドの最初の答えで知らせる。** 毎回知らせるとうるさいので、スレッドにまだ答えがないときと、答えの途中で見つけたときだけ、`{"notice":…}` で読んだファイルを知らせます。

### 待ち受けるアドレス

1. **既定は 127.0.0.1。** 会話の記録を持つので、何もしなければ同じ機械の中からだけ開けるようにしました(suru-lang/suru#117)。前は する が 0.0.0.0 でしか待ち受けられず、ファイアウォールで閉じるしかありませんでした。
2. **`--listen` で選ぶ。** `--listen 0.0.0.0` で、ほかの機械からも開けます。IPv6 なら `--listen ::1` のように書けます。HTTP ライブラリ 0.5.0 の `「アドレス:ポート」 を … で WebSocket内の待受する` に渡します。

### Ollama のライブラリ

1. **API は suru-lang/ollama で。** Ollama とのやりとり(`/api/chat` を流す・届いた行を断片・考え・道具呼出・完了・誤りに分ける、`/api/tags`・`/api/version`、web 検索 API)は、ほかのアプリでも使えるように [suru-lang/ollama](https://github.com/suru-lang/ollama) に分けました(#31)。`Ollama.suru` はなくなり、このアプリには会話帳の型から詰め替える [詰替.suru](詰替.suru) だけを置きます。
2. **送る発言はライブラリの型で持つ。** 答えの途中で足す発言(道具を呼んだ assistant の発言、道具の結果、頼み直し、読み直したリポジトリの決まり)も、JSON でなく `Ollama発言` で作ります。
3. **道具を回すのはこのアプリで。** 道具の回数の上限、画面への `{"running"}`・`{"tool"}`、頼み直しは、砂場と画面に絡むので、ライブラリには入れずに `本体.suru` に残しました。
4. **失敗の文はライブラリのもの。** Ollama が `{"error":…}` を返したときの「Ollama: model 'x' not found」、つながらないときの「…/api/chat に聞けませんでした: …」は、前と同じ文です。モデルの一覧を取れなかったときの 502 の文は、ライブラリの文をそのまま使います。web 検索の鍵が違うときは「Ollama に断られました(401: …)。鍵を確かめてください」になりました。

### 添付

1. **画像と文書は表 `添付` に。** 問いに添えたものは、発言ごとに表 `添付`(種類・名前・MIME・中身・文・ページの数)にしまいます。発言・スレッド・会話を消すと一緒に消えます(`ON DELETE CASCADE`)。データベースの1つのファイルに収まるので、写せば持ち運べます。
2. **画像は base64 の文字列のまましまう。** Ollama の `images` は base64 の文字列なので、送るたびに符号化し直さないように、受け取った base64 をそのまま `中身` に入れます(バイト列より 3 分の 1 ほど大きくなります)。`GET /api/attachments/番号` で見せるときだけ戻します。
3. **画像は画面で縮めて形をそろえる。** 長い辺 1600px まで、JPEG(透明があれば PNG)にしてから送ります。データベースが重くならず、HEIC・WebP など Ollama が読めないかもしれない形もそろいます。サーバーは PNG と JPEG だけを受け付け、base64 を読めるかも確かめます。
4. **PDF の文は画面で取り出す。** pdf.js を `画面/外/pdfjs/` に置いて、はじめて PDF を添えたときに読みます(CDN にはつながず、手元だけで動くように)。日本語の PDF のために `cmaps/` も置きました。サーバーに poppler などを入れずに済みます。元の PDF はしまわず、取り出した文とページの数だけをしまいます。
5. **文書はモデルに送るときに問いの前に入れる。** `<file name="報告.pdf">…</file>` で囲んで、問いの前に置きます。会話帳の `内容` には人が書いた問いだけを残すので、検索の見出しやスレッドの題が PDF の文で埋まりません(添えただけで書かずに送った問いは、はじめの添付の名前を題にします)。名前の `"`・`<`・`>` は除きます。
6. **一覧には目録だけ。** スレッドの中身の発言には添付の目録(番号・種類・名前・ページの数・字数)だけを付け、画像の中身はモデルに送るときだけ読みます。
7. **大きさに上限。** 画像は1つの問いに 8 枚・1 つ base64 で 1400 万字(元で 10MB ほど)まで、添える文は合わせて 10 万字まで、要求の本文は 30MB までです。画面でも先に断ります。
8. **画像は Ollama のライブラリで送る。** suru-lang/ollama 0.2.0 の `Ollama画像追加する` で、発言に `images` を付けます。
9. **文字のないページは画面で画像にする。** pdf.js でページを描いて(長い辺 1600px・白地の JPEG)、普通の画像の添付として送ります。サーバーは変えません。画像にしたページは、`<file>` の中を「(このページは画像で添えます)」にします。はじめから印を付けておき、上限(画像と合わせて 8 枚)を超えたら、はじめのページから画像にします。文のあるページを選んで画像にすることは、まだできません。
10. **画像を読めるかは Ollama の `/api/show` で。** `capabilities` に `vision` がなければ読めないモデルとします。`/api/models` を開くたびと、答えを作るたびに聞きます。答えを作るときは、モデル帳にあれば帳の能力を使い、なければ聞きます。`capabilities` がない古い Ollama や、聞けなかったときは止めません。
11. **読めないモデルに画像を送らない。** 最後の問いに画像があれば、サーバーも Ollama へ送る前に断ります。前の問いの画像は外して、内容の前に「(画像: 猫.jpg)」と書き添えて送ります(画像があったことはモデルに分かるように)。画面は、前の画像のあるスレッドで読めないモデルに変えると「前の画像は読まれません」と知らせます。

### モード

1. **モードは会話ごとに。** 会話帳の表 `会話` に `モード`(`会話`・`コーディング`)を足しました。スレッドは会話のモードを使います。新しい会話のモードは、画面が前に選んだものを覚えます。
2. **決まりに場面を付ける。** 表 `決まり` に `場面` を足し、「いつも」(前の「既定」)・「会話」・「コーディング」・「」(手で付ける)にしました。API の `"default"` も残し、`"default":true` は「いつも」と同じです。
3. **モードを変えると、場面の決まりを付け直す。** 前のモードの場面の決まりを外し、新しいモードの場面の決まりを付けます。手で付けた決まりと「いつも」の決まりはそのままです。付け直したあとに手で外すこともできます。
4. **見本の決まりはコーディングの場面に。** 「コードを書くときの決まり」は、中身を変えていなければ場面を「コーディング」にします(`user_version` 2)。
5. **コーディングモードでは、リポジトリの決まりをいつも読む。** 砂場か GitHub を使わない答えでも、作業フォルダの `OHANASHI.md` などを読みます。画面はコーディングモードにすると「💻 砂場」を押します(使えるとき)。

### モデル帳

1. **帳は会話帳と同じファイルに。** 表 `モデル帳`(名前・digest・大きさ・族・パラメータ・量子化・文脈長・能力・特徴・点数・注意・調べ役・調べた時刻・失敗・手直し)と、調べている様子の表 `モデル調べ`(1行)を足しました。Ollama からなくなったモデルは帳からも消します。
2. **起動を待たせない。** Ollama とつながったら、別のスレッドで `/api/tags` と `/api/show` を聞いて帳を合わせ、調べます。`digest` が同じモデルは聞き直さず、変わったモデルは調べ直す印を付けます。スレッドのあいだは、データベースの表で様子を分けます(調べる役は表の1行の `走` で1つだけ)。起動し直すと `走` を戻します。
3. **調べるのはウェブ検索があるときだけ。** SearXNG か Ollama の API キーがなければ、大きさ・能力だけを記録します(画面で手で書けます)。検索の言葉は「名前 LLM」と「族 パラメータ benchmark coding」で、それぞれのはじめの4つを渡します。モデルの名前はウェブ検索に送ります。
4. **答えの形は Ollama の `format` で決める。** `{"summary","scores":{"coding","chat","japanese","reasoning"},"notes"}` の JSON Schema を渡し、温度は 0 にします。JSON の前後に文や ``` があっても読み、点数が 0〜5 でない・特徴が空の答えは失敗として1回だけ頼み直します。
5. **調べ役の選び方。** `--research-model` → 前に調べたモデル → 最近の会話のモデル → 道具を使える一番大きいモデル → 一番大きいモデル の順です。`--research-max-size` があれば、それより大きいモデルは選びません(指名したモデルは除く)。
6. **貧弱なら1回だけ調べ直す。** 調べ役が 7B 未満か、半分以上失敗したら、道具を使えてパラメータが2倍以上のモデルのうち一番大きいもので、調べたモデルを調べ直します。調べ直しは1回だけです。
7. **調べ直すのは digest が変わったときと、頼まれたときだけ。** 「調べ直す」は `POST /api/models/research` です。手で直したモデルは調べ直しません。
8. **おすすめは会話を作るときだけ。** 点数のあるモデルから、モードの点数(コーディングは道具を使えるものから。なければ全部から)、日本語の点数、小ささの順で選びます。点数がなければ一番大きいモデル(コーディングは道具を使えるもの)。画面は点数のあるおすすめだけを使い、なければ前に選んだモデルにします。会話を作ったあとは、モデルを勝手に変えません。
9. **`keep_alive` と時間切れは決めていない。** suru-lang/ollama 0.2.0 にないので、調べるたびに Ollama の既定でモデルを読み込みます。大きなモデルに切り替えると、その間ほかの答えが遅くなることがあります。

### 作業フォルダのファイル

1. **数えるのは手元の sh。** `find` と `stat`(GNU の `stat -c` がなければ macOS の `stat -f`)で、作業フォルダのファイルの道・大きさ・変えた時刻を読みます。コンテナがなくても(会話を消したあとでも)一覧を出せます。`.git` と、`make_document` の下書きのフォルダ `.文書` は入れません。`.git` のあるフォルダ(`github_clone` で作ったもの)は中が多いので、フォルダの名前だけを出します。500 個までです。
2. **できたファイルは、答えの前と後の一覧を比べて見つける。** 砂場を使う答えでは、始める前に一覧を読み、終わったときにもう一度読んで、新しいか、大きさか時刻が変わったファイルを `{"files":…}` で画面に送ります。`run`・`write_file`・`make_document` のどれで作っても同じに見つかります。
3. **リンクは答えといっしょに保存し、モデルには送らない。** 画面は `files` を受け取ったら、答えの終わりに「📄 [名前](道)(大きさ)」の行を足して保存します。道具の跡と同じく、「📄 」で始まる行は次にモデルへ送るときに除きます。
4. **配るのは suru-lang/http の `前置付配信する`。** その会話の作業フォルダの中だけを配ります。「..」「.」「\」、`%00`、フォルダの外を指すシンボリックリンクは 403、「.」で始まる名前は 404 です。
5. **落とすのが基本。** `Content-Disposition: attachment` を付けます。PDF と画像(PNG・JPEG・GIF・WebP)だけは、`?view=1` で `inline` にしてブラウザで開きます。モデルが書いた HTML や SVG が、この画面と同じ所でスクリプトを動かさないように、`X-Content-Type-Options: nosniff` と(PDF のほかは)`Content-Security-Policy: sandbox` も付けます。docx・xlsx・pptx の `Content-Type` はアプリで持ちます。

### 文書を作る

1. **文書は砂場で作る。** サーバーは pandoc などを持たず、Markdown をコンテナの `/work/.文書/元.md` に書いて、コンテナの中の `/opt/ohanashi/文書.py` で変えます。手元を汚さず、モデルの書いたものを手元で動かしません。
2. **道具は1つ、モデルは Markdown を書くだけ。** `make_document`(`format`: `pdf`・`docx`、`path`、`markdown`、`title`)です。小さいモデルでも python-docx のコードを書かずに作れます。`path` を省くと `出力/題.拡張子` にします。`/work` の外や「.」で始まる名前は断ります。結果は「📄 出力/報告.pdf を作りました(3 ページ・48KB)」です。
3. **docx は pandoc の既定、PDF は pandoc → HTML → WeasyPrint。** 日本語のフォントと CSS([砂場/文書.css](砂場/文書.css)。A4、表の罫線、ページ番号)が使えます。LaTeX と LibreOffice は大きいので入れていません。
4. **文書を作れるイメージかは、イメージの印で見る。** `砂場/Dockerfile` に `LABEL ohanashi.documents="1"` を付け、起動のときに `docker image inspect` で見ます。印があれば `make_document` を渡し、案内にも「Word や PDF を頼まれたら make_document を使う」と書きます。`--sandbox-image` を付けなければ、`ohanashi-sandbox` があればそれを使います。
5. **版は固定する。** 元のイメージは `python:3.12-slim-bookworm`、pip で入れるもの(WeasyPrint 62.3 と、それに合う pydyf 0.11.0 など)は版を書きます。pandoc とフォントは Debian bookworm のものです。
6. **作ったと書いただけなら、一度だけ頼み直す。** 答えに「作成しました」「作りました」「ダウンロード」などと、`.docx`・`.pdf` などの名前があるのに、その答えの中で作業フォルダにファイルができていなければ、GitHub の push・PR と同じく、道具で作るように頼み直します。それでもできなければ「⚠ ファイルはできていません」と出します。前の答えでできたファイル(「📄 」の行にある名前)を、また書いても知らせません。
7. **できたファイルは添付にしない。** 作業フォルダにあれば十分なので、会話の添付(画像・PDF を読ませるもの)には入れません。モデルに読ませたいときは、落として 📎 で添えます。

### 通知

1. **画面だけで作る。** 答えの終わりは、画面が `{"done":true}`(fetch のときは流れの終わり)で分かるので、`答えてもらう()` の終わりで知らせます。サーバーは変えていません。
2. **見ていないときだけ知らせる。** タブが隠れている(`document.hidden`)か、窓にフォーカスがないときだけです。自分で「止める」を押したときは知らせません。
3. **タブの題の印は、いつも付ける。** 見ていない間に終わったら、タブの題の頭に「✅ 」(失敗は「⚠️ 」)を付け、タブを見たら外します。ブラウザの許しが要らず、ほかの機械から http で開いたときも使えるためです。
4. **通知は ⚙ で入れたときだけ。** 「🔔 見ていない間に答えが終わったら通知する」に印を付けたときに、ブラウザに許しを聞きます(Safari などは、押したときでないと聞けないため)。いきなり許しを聞く窓を出さないように、既定では入れません。会話ごとではなく、このブラウザの設定として localStorage にしまいます。
5. **通知の中身。** 題はスレッドの題、本文は途中経過を除いた答えの頭(Markdown の記号を除いて 100 文字まで)です。失敗は「失敗しました: …」。`tag` をスレッドごとにして、同じスレッドの通知は1つにまとめます。押すと、そのタブに戻ってそのスレッドを開きます。タブを見たら、出した通知を閉じます。中身を作るところは `画面/通知.js` にまとめ、`node 道具/通知試験.js` で確かめます。
6. **通知は安全な場所でだけ。** ブラウザの通知は localhost か https で開いたときだけ使えます。ほかの機械から `http://192.168.…` で開いたときは ⚙ の印を押せなくして、その理由を出します。音は鳴らさず、OS の通知の音に任せます。
7. **タブを閉じていると届かない。** タブを閉じていても届けるには Service Worker と Web Push が要り、https と鍵の用意とサーバーの変更も要るので、今はしていません。

### https

1. **TLS は Tailscale Serve に任せる。** http ライブラリの HTTPS はクライアントだけで、サーバーの TLS はありません。する の「通信」のソケットは OS の fd ではないので、サーバーの TLS を作るには本体と http ライブラリの両方に手が要ります。ほかの機械から開くのは Tailscale を使うことが多いので、証明書の用意も更新もしてくれる Tailscale Serve を前に置くことにしました(#75・#76)。
2. **Origin は http と https のどちらでも。** Tailscale Serve は Host をそのまま渡すので、https で開くと `Origin` が `https://` + Host になります。`Origin` が `http://` + Host か `https://` + Host なら受け付け、ほかのサイトからは今のとおり断ります。
3. **WebSocket は画面の URL から。** 画面は `location.href` の `http` を `ws` に変えて WebSocket の URL を作るので、https で開けば `wss://` になります。

### する 0.9.1

1. **する 0.9.1 以上が要る。** 使うライブラリの http 0.7.0 と sqlite 0.4.0 が、C の関数を 0.9.1 で入った「以下は外部の入出力動作です … 以上です」で書いているためです。それより古い `kumu` では組めません。
2. **砂場の C の関数は1行で書く。** 型の宣言と定義の2行を `s を 命令渡しする とは 外部の「system」 で 文字列 を 受け取って 整数 を 返す 入出力動作です` の1行にして、名前を1回で済ませました。C の関数は1つだけなので、「以下は外部の入出力動作です」のまとまりにはしません。
